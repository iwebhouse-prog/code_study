# TASK-039. 회원가입 브라우저 테스트

## 상태
완료

## 날짜
2026-11-09

## 작업 요약
실제 브라우저(Chrome)에서 새 계정으로 가입해 보고, 서버가 성공으로 답하는지와 가입 후 알맞은 화면으로 옮겨 가는지 확인했습니다. 지금까지는 백엔드와 프론트엔드를 따로따로 시험했는데, 이번에는 두 쪽을 실제로 함께 켜 놓고 손님 입장에서 처음부터 끝까지 따라가 본 것입니다. 새 가구를 설명서대로 조립한 뒤 실제로 앉아 보는 것과 같습니다.

진행 순서와 결과는 다음과 같습니다.

1. 로그인하지 않은 상태에서 회원가입 화면(`/register`)을 엽니다. 이메일·비밀번호 입력칸, 가입 버튼, 로그인 화면으로 가는 링크가 보였습니다.
2. 확인용 계정 `e2e-t039@example.com`으로 가입했습니다.
3. 서버가 **201(새로 만들었음)** 으로 답했습니다. 그 직전에 브라우저가 "이 요청을 보내도 되는지" 묻는 사전 확인(OPTIONS)도 200으로 통과했습니다.
4. 가입하자마자 로그인된 상태가 되어 **대시보드("내 프로젝트")로 이동**했습니다(계약 문서의 약속대로).
5. 로그인 쿠키는 페이지의 자바스크립트에서 보이지 않았습니다. 쿠키가 HttpOnly로 보호되고 있다는 뜻입니다.
6. 콘솔 오류는 없었습니다.

## 왜 이렇게 시험했나
- 단위 테스트는 각 부품이 약속대로 움직이는지만 봅니다. 실제 주소, 쿠키, 브라우저 보안 규칙(CORS)이 맞물리는지는 진짜 브라우저에서만 알 수 있습니다.
- 브라우저의 네트워크 기록을 처음부터 켜 두고 진행해, 화면 이동뿐 아니라 서버의 실제 응답 번호까지 증거로 남겼습니다.

## 관련 개념
- **사전 확인 요청(preflight)**: 다른 주소(5173 → 8000)로 데이터를 보내기 전에 브라우저가 서버에 허락을 먼저 받는 절차입니다.
- **종단 간 시험(E2E)**: 화면부터 서버, 데이터베이스까지 실제 부품을 모두 연결해 사용자가 하는 그대로 따라가 보는 시험입니다. 부품 시험이 모두 통과해도 연결 부분에서 문제가 생길 수 있어서 따로 합니다.

## 주의할 점 (비고)
- 이미 로그인한 사람이 가입 화면에 들어와도 자동으로 다른 화면으로 보내지 않습니다.
- 시험 계정 `e2e-t039@example.com`, `e2e-auth-1109@example.com`이 개발 DB에 남아 있습니다.
