# TASK-045. 프로젝트 소유자 확인

## 상태
완료

## 날짜

## 작업 요약
**내 공책(프로젝트)은 나만 보고 고칠 수 있게** 하는 확인 장치를 넣었습니다. 도서관 사물함에 비유하면, 사물함 번호를 안다고 아무나 여는 것이 아니라 열쇠 주인인지 확인한 뒤에만 열어 주는 것입니다.

창구 직원(ProjectService)에게 "누가 요청했는지"를 함께 받는 업무 세 가지를 새로 만들었습니다.

| 새 업무 | 하는 일 |
|---|---|
| `get_for_user` | 공책을 꺼내 주되, 주인이 아니면 거절 |
| `update_for_user` | 주인일 때만 고침 |
| `move_to_trash_for_user` | 주인일 때만 휴지통에 넣음 |

답하는 방식은 다음과 같습니다.

- 공책이 없거나 휴지통에 있음 → 404 "요청한 프로젝트를 찾을 수 없습니다…"
- 공책은 있지만 남의 것 → **403 "이 프로젝트에 접근할 권한이 없습니다."** (명세 CHK084의 문장)
- 거절할 때는 누가 어느 공책을 열려 했는지 기록을 남깁니다(명세 FR-110 권한 실패 기록).

## 왜 이렇게 만들었나
- **기존 업무는 그대로 두고 새 업무를 더했습니다.** T044 테스트는 "누가"를 받지 않는 형태로 기존 업무를 부릅니다. 테스트는 고칠 수 없으므로 형태를 바꾸지 않았습니다. 대신 설명문에 "API 주소에서는 반드시 `_for_user`를 쓸 것"이라고 적었습니다.
- **같은 일을 두 번 쓰지 않았습니다.** 실제로 고치고 휴지통에 넣는 부분은 공통 함수 하나로 모아, 기존 업무와 새 업무가 함께 씁니다.
- **남의 것을 고치려 해도 아무것도 바뀌지 않습니다.** 주인 확인이 바꾸기 전에 일어나기 때문입니다(테스트로 확인).

## 기술 결정
- 403과 404를 구분했습니다. 보안만 보면 남의 공책도 404로 답해 존재를 숨기는 방법이 있지만, 명세가 403 문장을 따로 정해 두어 그대로 따랐습니다. 공책 번호는 추측하기 어려운 무작위 값(UUID)이라 존재 여부가 드러나도 위험이 작습니다.
